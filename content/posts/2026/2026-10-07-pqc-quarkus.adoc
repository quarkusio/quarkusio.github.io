Quantum computing is progressing fast, and the cryptographic threat it poses is not purely a
future concern: adversaries can collect your encrypted traffic *today* and decrypt it once a
sufficiently capable quantum computer becomes available. This pattern is known as _harvest now, decrypt later_, and there is no technical barrier preventing it today.

The good news: a new post-quantum key exchange standard is ready and Quarkus 3.39 integrates it.
This post gives an overview and a quick start; the link:/guides/post-quantum-cryptography[Quarkus PQC guide] covers the full background and a step-by-step tutorial.

== TLS 1.3 in one minute

Encrypting data between two parties requires a shared secret key: both sides use it to encode and decode messages with AES, a symmetric cipher that is fast and secure.
The challenge is agreeing on that key over a public network where anyone can eavesdrop.
This is the role of *asymmetric cryptography* (or *key exchange*): each party holds a private value that is never transmitted, and derives from it a *key share*: a bundle containing the public value and the identifier of the group (algorithm and parameters) used to generate it, so the other side knows how to combine it with their own private value to arrive at the same shared secret.
Anyone watching the network only sees the key shares, which are not enough to reconstruct the secret.
The dominant protocol today is *X25519*, an Elliptic-Curve Diffie-Hellman scheme based on the hardness of the elliptic curve discrete logarithm problem.

A TLS 1.3 handshake establishes a secure session in a single round trip by combining these mechanisms.
The client opens with a `ClientHello` listing its supported key exchange groups and an initial key share for its preferred group.
The server picks a group, contributes its own share in a `ServerHello`, and both sides independently derive the same shared secret without ever sending that secret over the wire.
The server immediately uses that secret to encrypt the rest of its handshake messages, and sends its certificate together with a signature over the transcript, proving ownership of the private key associated with the certificate.
The client verifies the certificate against its trust store and checks the signature, completing *authentication*.
From that point on, all application data is protected with AES (*symmetric encryption*) using a key derived from the shared secret.

image::tls_13_handshake.png[TLS 1.3 handshake overview, align="center"]

Not all three mechanisms (key exchange, authentication, and symmetric encryption) are equally exposed to quantum computers, which is where post-quantum key exchange becomes relevant.
The link:/guides/post-quantum-cryptography[Quarkus PQC guide] covers TLS and the underlying mathematics in depth, including a walkthrough of Diffie-Hellman and ML-KEM.

== Key exchange: today's weak link

*Authentication* is less urgent: forging a certificate requires a quantum computer operating live at connection time, not one that runs years later on recorded traffic.

*Key exchange*: the handshake step where client and server agree on a shared secret is
vulnerable today: anyone recording your TLS traffic can store the exchanged parameters and, once
a capable quantum computer is available, apply Shor's algorithm to break the private key in polynomial time.

*Symmetric encryption*: Grover's algorithm halves effective key strength, but AES-128 as used in `TLS_AES_128_GCM_SHA256` is generally considered adequate for post-quantum security. No action required.

[cols="1,1,2,2", options="header"]
|===
| Job | Algorithm today | Quantum attack | Urgency

| Symmetric encryption
| AES-128
| Grover's algorithm halves key strength
| Low - AES-128 is generally considered adequate for post-quantum security

| Key exchange
| X25519 (ECDH)
| Shor's algorithm breaks it in polynomial time
| High - harvest now, decrypt later applies today

| Authentication
| RSA / ECDSA
| Shor's algorithm breaks it in polynomial time
| Low - requires a quantum computer operating in real time at connection time
|===

Key exchange is therefore the urgent piece. ML-KEM-768 is a new quantum-resistant key encapsulation mechanism standardized by NIST as link:https://csrc.nist.gov/pubs/fips/203/final[FIPS 203], based on different mathematical hardness assumptions that Shor's algorithm cannot exploit. Rather than replacing X25519 outright, the standard opted for a hybrid: *X25519MLKEM768* runs both protocols in parallel, derives a secret from each, and combines them into the final shared key using a Key Derivation Function _KDF_. The hybrid design
ensures that if either component is secure, the combined secret is secure.
Concretely, the first two messages of the TLS handshake shown above now carry both contributions at once, and both sides independently derive the same final key:

image::x25519mlkem768_2.png[X25519MLKEM768 hybrid key exchange overview, align="center"]

See the link:/guides/post-quantum-cryptography[Quarkus PQC guide] for the full mathematical background behind both algorithms and how Shor's algorithm threatens classical key exchange.

== Enabling PQC in Quarkus

Quarkus exposes three properties for controlling post-quantum key exchange:

[source,properties]
----
quarkus.tls.pqc-enforcement-policy=client-negotiated   # relaxed | client-negotiated | strict
quarkus.tls.ssl-engine=openssl                         # jdkssl | openssl
quarkus.tls.key-exchange-groups=X25519MLKEM768,X25519  # any list of TLS named group
----

`pqc-enforcement-policy` is the simplest starting point: it drives both engine selection and group resolution automatically, so you rarely need to touch the other two.

[NOTE]
====
On JDK 27+, X25519MLKEM768 is negotiated by default without any configuration. The `pqc-enforcement-policy` property is not needed to enable PQC; it exists to guarantee it (rejecting peers that do not support it) and to fail fast at startup if the runtime ends up without a PQC-capable engine.
====

Three policy values are available:

* `client-negotiated`: the server supports PQC but falls back to classical groups for clients that
don't advertise it. Startup fails if no PQC-capable SSL engine is available.
* `relaxed`: no enforcement; classical groups are accepted (the default behavior).
* `strict`: only PQC-compliant key exchange is accepted; non-PQC clients are rejected and startup
fails if no PQC-capable SSL engine is available.

`client-negotiated` is the recommended starting point for a server: it advertises PQC and uses it with clients that support it, but falls back to classical groups for others so existing peers are not disrupted:

[source,properties]
----
quarkus.tls.pqc-enforcement-policy=client-negotiated
----

[WARNING]
====
`strict` rejects any peer that does not advertise PQC groups. On a server this includes older clients, health checks, and load balancers. On a client it causes failures against any server that does not support PQC, including third-party APIs. Only use `strict` when all peers are known to support PQC.
====

The runtime selects the right SSL engine automatically based on your policy and JDK version; if the user specified an engine that is not PQC-capable, the app fails at startup. If the user specified a key exchange groups list that is incompatible with the policy (e.g. only classical groups under `strict`), Quarkus overrides it with PQC-compliant groups.

=== Prerequisites by JDK version

[cols="1,2", options="header"]
|===
| Runtime | How PQC is provided

| JDK 27+
| JdkSSL (built-in) or OpenSSL (`smallrye-openssl`)

| JDK 25
| JdkSSL after the October 2026 Critical Patch Update (check your vendor), or OpenSSL (`smallrye-openssl`)

| JDK 17 / 21
| OpenSSL (`smallrye-openssl`) only; JdkSSL backport expected in the first half of 2027
|===

Dates follow the link:https://www.java.com/en/jre-jdk-cryptoroadmap.html[Oracle JRE and JDK Cryptographic Roadmap] and may change.

For JDK < 27, install OpenSSL 3.5+ and `libapr-1` on the host machine (Linux x86_64 or aarch64 only; on UBI-based container images: `microdnf install -y apr`), then add these dependencies to `pom.xml`:

[source,xml]
----
<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-tcnative-classes</artifactId>
</dependency>
<dependency>
    <groupId>io.smallrye</groupId>
    <artifactId>smallrye-openssl</artifactId>
</dependency>
<dependency>
    <groupId>io.smallrye</groupId>
    <artifactId>smallrye-openssl</artifactId>
    <classifier>linux-x86_64</classifier>  <!-- or linux-aarch_64 -->
</dependency>
----

link:https://github.com/smallrye/smallrye-openssl[smallrye-openssl] and `libapr-1` are necessary due to the way the OpenSSL integration works under the hood; the link:/guides/post-quantum-cryptography[Quarkus PQC guide] covers the technical details.

[NOTE]
====
The OpenSSL path is JVM-only. In native mode, `smallrye-openssl` is not available, and JdkSSL
PQC support is also pending a future Mandrel release built on a PQC-capable JDK.
====

=== Seeing it in action

With the server set to `strict`, a client that advertises only classical groups is rejected:

[source,bash]
----
openssl s_client -connect localhost:8443 -groups X25519
# → ssl/tls alert handshake failure
# → Negotiated TLS1.3 group: <NULL>
----

The same property applies to REST clients, scoped to a named TLS configuration:

[source,properties]
----
# Apply PQC to the named "client" TLS configuration
quarkus.tls.client.pqc-enforcement-policy=client-negotiated
quarkus.rest-client."org.acme.GreetingClient".tls-configuration-name=client
----

With the client advertising PQC groups, `openssl s_client` (OpenSSL 3.5+) confirms the negotiated group:

[source,bash]
----
openssl s_client -connect localhost:8443
# → Negotiated TLS1.3 group: X25519MLKEM768
----

The initial contributions are available in Vert.x 4.5.28+ and Vert.x 5.1.0+, and were integrated in Quarkus 3.39.

== What's next?

This release covers key exchange. Several areas remain open:

* *Clients outside the TLS registry* such as Kafka consumers/producers and JDBC drivers are not
  yet covered by the enforcement policy. On JDK 27+ those connections advertise X25519MLKEM768 by
  default; on older JDKs they negotiate classical groups regardless of Quarkus configuration.
* *Native mode* support is pending a future Mandrel release built on a PQC-capable JDK.
* *Non-Linux platforms* (macOS, Windows, IBM Power, IBM Z) are not yet supported by `smallrye-openssl`.
* *Post-quantum signatures* (ML-DSA) for certificate authentication remain a separate effort;
  certificate-based mutual authentication still uses classical RSA/ECDSA.
