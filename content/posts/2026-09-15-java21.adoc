Quarkus 4 is coming, and one key decision was raising the Java baseline to 21. This post explains why.

Let's be clear: nothing is wrong with Java 17. This isn't about something broken. It's about where we're heading.

== Virtual threads, for real this time

Java 21 is the first LTS with virtual threads. Quarkus 3 already supported them, but through reflection hacks to avoid depending on the Java 21 API (https://github.com/quarkusio/quarkus/pull/56328[Here's what that looked like]). Hard to maintain, poor performance, and a convoluted fallback. Worse, virtual threads felt like second-class citizens; not every extension was tested with them.

With Java 21 as the baseline, that changes. No reflection, no conditional paths. We test the framework with virtual threads in CI and catch issues before you do. You keep using simple, blocking APIs, and get the scalability benefits without having to embrace the reactive path.

If you're an extension writer: expect a much simpler path to support virtual threads.

== The ecosystem is moving

We're not early. Projects are already dropping Java 17:

- https://errorprone.info/docs/installation[Error Prone] requires Java 21
- https://www.jenkins.io/doc/book/platform-information/support-policy-java/[Jenkins CI] no longer supports Java 17
- https://jena.apache.org/download/index.cgi[Apache Jena 6] requires Java 21

https://jakartaee.github.io/platform/jakartaee12/JakartaEE12ReleasePlan[Jakarta EE 12] sets Java 21 as the platform baseline. Each spec can decide to stay on 17, but none can go higher than 21. If Quarkus 4 started at 17, we'd need a mid-lifecycle bump to adopt these specs. That's exactly what we want to avoid.

== Java 17 is on the clock

Some said, "Java 17 is EOL, no-brainer." The reality depends on your JVM vendor; support ends in 2027 or 2029. But Quarkus 4 will live for several years. We wanted to be ahead of these dates, not chasing them.

== A leaner build matrix

Quarkus currently tests against Java 17, 21, and the next LTS preview. Dropping 17 means two LTS versions instead of three. With Java 29 on the horizon, keeping 17 would mean four. Less CI time, fewer flaky permutations.

== Why not 25?

Great question. Our usage data still shows strong Java 21 adoption. Java 25 has benefits, but Quarkus already supports it, including FFM, without a hard dependency. Native compilation uses Mandrel 25 regardless.

image::quarkus-java-version.png[Evolution of Java version usage]

== What changes for you?

Not much. Java 21 usage (blue) is growing; Java 17 (green) is declining. Quarkus 4 is heading where our community already is. The first RC is planned for the end of September.

**If you're on 21+, nothing changes. If you're on 17, now is a good time to plan the move.**
